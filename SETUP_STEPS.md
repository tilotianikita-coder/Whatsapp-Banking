# LoanSeva — manual setup steps

Everything that could be source-controlled is in `force-app` and deploys with `sf project deploy start`. The steps below were **unavoidable manual or org-level** actions, either because the platform has no metadata/API path in this org or because they need a human (Meta approval, real phone numbers). Do them in order after a deploy.

## 1. Deploy, assign, seed

```bash
scripts/deploy.sh force-app
sf apex run -f scripts/apex/create_agent_user.apex -o kotak-demo   # once: Einstein Agent User "loanseva.agent.*"
sf apex run -f scripts/apex/post_deploy.apex -o kotak-demo         # perm sets (guest, agent user, you) + drop-off job
```

1. Edit the `DEMO_MOBILES` list at the top of `scripts/apex/seed.apex` with the presenters' WhatsApp numbers (10 digits, no +91). Order: Priya, Rahul, Ananya.
2. Run `sf apex run -f scripts/apex/seed.apex -o kotak-demo`. Re-running resets the demo journeys for those numbers, so run it before every demo.

## 2. Public registration site (Stage 0)

The `LoanSeva` site, its Visualforce page and the guest permission set are all deployed. The site is Active, and the guest profile "LoanSeva Profile" has access to `LoanSevaRegister` and the error pages. **At the time of writing the public URL still returns HTTP 503 "down for maintenance" for every page, including a controller-less test page.** No request reaches Apex, so this is an org/site-level state, not a code issue.

Check in **Setup → Sites**:

1. Sites → **LoanSeva** → confirm **Active** and Active Site Home Page = `LoanSevaRegister`. Toggle **Deactivate → Activate** once if needed.
2. Sites (list page) → confirm the org's Sites domain is registered and **not** shown as "in maintenance". Trial and Developer orgs sometimes need the domain re-saved (Setup → **Domains** / **My Domain** → the `*.my.salesforce-sites.com` entry).
3. LoanSeva → **Public Access Settings** → Visualforce Page Access includes `LoanSevaRegister`; Enabled Apex Class Access includes `LoanSevaRegisterController`.
4. Setup → **Sharing Settings / Guest user access**: nothing else is required. The guest only publishes `LoanSeva_Event__e`, and the subscriber runs as the admin (`LoanSevaEventTriggerConfig`).

Test URL: `https://trailsignup-5e5549adddf5d7.my.salesforce-sites.com/loanseva?src=qr` (the same URL is encoded in `docs/LoanSeva_Registration_QR.png`).

**Demo fallback:** logged-in users can open `https://<my-domain>.my.salesforce.com/apex/LoanSevaRegister?src=link`. It is the same page, controller and flow. If you move to a different site or domain, regenerate the QR:

python3 -c "import segno; segno.make('<URL>?src=qr', error='m').save('docs/LoanSeva_Registration_QR.png', scale=12, border=2, dark='#003874')"

## 3. Agent (deployed and activated from source)

`sf agent publish authoring-bundle` returns **404 AgentApiNotFound** in this org, so the agent is deployed as classic Agentforce metadata instead: `bots/LoanSeva_by_Kotak` (Bot + BotVersion v1, Service Agent, running user `loanseva.agent.00dgl00000eqlv3@example.com`), `genAiPlannerBundles/LoanSeva_by_Kotak`, 3 topics in `genAiPlugins` (Top-Up Journey, Language Switch, Escalate to Human) and 13 actions in `genAiFunctions`. All of it is generated by `scripts/gen_classic_agent.py`.

Journey routing is deterministic: every customer reply goes to `LoanSevaReplyAction` → `LoanSevaEngine.reply()`, which dispatches on the saved journey state.

To change the agent:

```bash
PYTHONPATH=scripts python3 scripts/gen_classic_agent.py
sf agent deactivate --api-name LoanSeva_by_Kotak -o kotak-demo      # active versions can't be edited
sf project deploy start -d force-app/main/default/genAiFunctions -d force-app/main/default/genAiPlugins -d force-app/main/default/genAiPlannerBundles -d force-app/main/default/bots -o kotak-demo
sf agent activate --api-name LoanSeva_by_Kotak -o kotak-demo
```

Test without WhatsApp: `sf agent preview -n LoanSeva_by_Kotak -o kotak-demo`. The Agent Script bundle (`aiAuthoringBundles/LoanSeva_by_Kotak`, `scripts/gen_agent.py`) is kept for orgs where the publish API works.

**Redeploying the agent breaks open conversations.** A WhatsApp session that is open while the agent is deactivated and reactivated fails on the next customer message, which gets the platform's generic "issue processing your request" reply. End open sessions first: in the Service Console, open each Active `MessagingSession` and click **End Conversation**. Or do it before the demo, and have the customer send a fresh **Hi**.

## 4. Route WhatsApp_BYOC conversations to the agent (Omni-Channel)

Automated from source; run after step 3.

1. `force-app/main/default/flows/LoanSeva_WhatsApp_Inbound_Routing.flow-meta.xml` is our own copy of the package template `wpbyocdemo3__TEMPLATE_WhatsApp_Inbound_Routing`; the managed flow is untouched. It routes inbound sessions to *LoanSeva by Kotak*, falls back to the `SDO_Service_Messaging` queue, and deploys as Active. It holds kotak-demo record ids (the `sfdc_livemessage` service channel and the bot). In another org, update `serviceChannelId` and `botId` before deploying.
2. `scripts/route_whatsapp.sh` points `WhatsApp_BYOC` at the flow (Omni-Flow routing, fallback queue `SDO_Service_Messaging`). `scripts/route_whatsapp.sh --queue` rolls back to plain queue routing.
3. **Specialist requests** ("agent", "human", "specialist", "RM", menu option 3, and Hindi/Marathi equivalents) are handled by `LoanSevaEngine.reply`. It always creates a `LoanSeva: Human requested - …` Task for the RM, and returns `handoff = true`. The journey topic then escalates the conversation, and Omni-Channel routes it to the channel's fallback queue `SDO_Service_Messaging`.
4. Manual, for the live takeover: the human must be a member of that queue (the demo RM is, via the *Service - Agents* group). Open the **Service Console**, then **Omni-Channel** in the utility bar, set the status to **Messaging - Available**, and accept the incoming WhatsApp session. Replies typed in the console go to the customer's WhatsApp. If nobody is online, the chat waits in the queue and the RM Task covers the 24-hour callback.

## 5. Go live on WhatsApp sends (nudge + re-engagement)

`LoanSeva_Config__mdt.Default.Send_Mode__c` is now `ConversationMessage`, so nudges are really sent. In `LogOnly`, the text is composed and stored in `Loan_Journey__c.Last_Send_Status__c` but not sent. Tests pin `LogOnly` themselves.

1. Already set in source (`scripts/content.py` → `customMetadata/LoanSeva_Config.Default.md-meta.xml`) and deployed:
   - `Send_Mode__c` = `ConversationMessage` (real send through the BYOC channel). Set it back to `LogOnly` to compose and log without sending.
   - `RM_Owner_Username__c` = `trailsignup.5e5549adddf5d7@salesforce.com`, so RM Tasks and Events are assigned to the demo RM.
   - Optionally tune `Idle_Minutes_Before_Drop__c` (2), `Nudge_1_Delay_Minutes__c` (2) and `Nudge_2_Delay_Minutes__c` (5). Production values would be 1440 / 4320.
   To change these, edit `scripts/content.py`, regenerate and redeploy.
2. **Activate the messaging component (one click, required).** Setup → **Messaging Components** → **LoanSeva Text** → **Activate**. Deployed components arrive inactive, and there's no API or metadata field to activate them. While it's inactive, the send is accepted (`Last_Send_Status__c = Sent …`) but fails asynchronously with `MessagingComponentNotActive`. To check, query `SELECT Name, FailedMessageCount, FailedMessageErrorReasons FROM ConvMessageSendRequest ORDER BY CreatedDate DESC`.
3. **Register every presenter number with the WhatsApp router (per number, required).** The BYOC business number is shared, and the package's router app picks the org for each inbound message by the *sender's* number. An unregistered number gets the WhatsApp reply "No routing configuration found", and nothing reaches Salesforce (no MessagingSession, no log). Open the app launcher → **WhatsApp Demo Component** tab (the router portal, `https://trailsignup-dbbab11c8f3410.my.site.com/whatsapp?username=<your username>`) and add each number in `DEMO_MOBILES` (with country code, e.g. `919063480755`) against this org. Then send "Hi" from each phone, which also opens the 24-hour window for the nudge text.
4. **WhatsApp template (Meta).** A business-initiated first message needs an approved template. Create a *Utility* template in Meta Business Manager, for example:
   > Hi {{1}}, great news from Kotak! 🎉 You're pre-qualified for a Personal Loan Top-Up of up to ₹{{2}} on your existing loan. Get a personalised offer in about 90 seconds — right here on WhatsApp.
   > Button (quick reply): **Continue Here!**

   Map it in the BYOC package's router settings (`WhatsApp_BYOC_Setting__mdt` / router admin) as the package documents. Until it's approved, the nudge goes out as the `LoanSeva_Text` free-text definition. That text is delivered only inside the 24-hour customer service window, so have each presenter send "Hi" to the business number once before the demo.
5. Run `sf apex run -f scripts/apex/seed.apex -o kotak-demo`, submit the registration form with a seeded number, and confirm the message arrives. `Loan_Journey__c.Last_Send_Status__c` shows `Sent …` or the exact failure reason. Package-side delivery errors show in `wpbyocdemo3__Debug_Log__c`.

## 6. Drop-off job

`post_deploy.apex` schedules `LoanSevaDropOffJob`, which re-runs every `Job_Interval_Minutes__c` (1). To control it by hand in anonymous Apex:

```apex
LoanSevaDropOffJob.start(); // (re)schedule
LoanSevaDropOffJob.stop();  // unschedule
LoanSevaDropOffJob.run();   // one pass now
```

## 8. WhatsApp reply-button test (optional)

`LoanSeva_Buttons_Test` is a test-only messaging component with three reply buttons (Accept offer, Change amount, Ask a question). It checks whether the shared WhatsApp BYOC router renders interactive buttons. Buttons can't go out as proactive sends: `sendConversationMessages` only takes Notification components, and those can't carry options. So it's sent by a human agent inside a live chat:

1. Setup → **Messaging Components** → **LoanSeva Buttons Test** → **Activate**. Deployed components arrive inactive (see §5 step 2).
2. From the test phone, message the WhatsApp number and reply **3** (Talk to a specialist). The chat routes to the LoanSeva queue.
3. In the Service Console, accept the chat. In the conversation composer, open the messaging components picker (⚡ icon), choose **LoanSeva Buttons Test** and send it.
4. On the phone, check what arrives. Tappable buttons mean the router supports interactive messages. A plain list or nothing means it doesn't. Then end the chat.

## 9. New-loan applications, mock underwriting and RM decision

Customers without a pre-approved offer can apply on WhatsApp. This happens when "Not found" / "no offer" follows identity, or via menu option **4**, or by typing "apply for a new loan". They're asked 10 questions (DOB, PAN, email, PIN, employment, employer, income, EMIs, purpose, amount) and shown an indicative offer. They then share photos of their PAN, bank statement and salary slips (each can be skipped), review, and consent. On submit:

- The customer gets a `KMB-PL-…` reference. A Contact is created if needed, and an RM Task is created on the application.
- **Mock underwriting** runs automatically: six `Underwriting_Check__c` rows (PAN/NSDL, CIBIL, Perfios bank statement, employment, policy & FOIR, dedupe). It sets `Recommendation__c`. No external calls are made.
- The RM opens the application in the **LoanSeva LOS** app. Across the top, **Credit Review** shows horizontal stage gates: Application → Documents → KYC (NSDL) → Bureau (CIBIL) → Banking (Perfios) → Employment (EPFO / GST) → Policy (FOIR) → Fraud (Hunter) → RM decision → Loan account. The colours are green = pass, yellow = refer/pending, red = fail, blue = awaiting the RM and grey = not reached. Clicking a gate opens that provider's mock report: key facts, flags and tables such as CIBIL accounts and enquiries, the Perfios monthly summary and spend pattern, PF contributions or GST filings, the policy grid, and Hunter rules and watchlists. The **RM credit summary** beside it gives the verdict, a narrative, strengths, risks and the conditions to clear before disbursal. Mock reports are seeded from the PAN, so the same file always shows the same data.
- The sidebar has the **Underwriting Scorecard**, with **Approve & create LAN**, **Reject** and **Re-run underwriting**. Approve creates a *Sanctioned* `Existing_Loan__c` (LAN `PL` + yyMMdd + 8-digit sequence) and WhatsApps the customer the terms with the **masked** LAN only. Reject sends a polite decline. RM notes stay internal.

**Demo PANs** pick the outcome. The format is `AAAPS9999X`: 4th character **P** (individual), 5th character = **surname initial**.

| PAN (for "Asha Patil") | CIBIL | Recommendation |
|---|---|---|
| `ABCPP1234K` + bank statement shared + Category A employer (e.g. Infosys) | 777 | Approve |
| `ABCPP1234K`, bank statement skipped | 777 | Refer (statement pending) |
| `ABCPP1234R` | 695 | Refer |
| `ABCPP1234Z` | 630 | Decline |
| `ABCPS1234K` (surname initial mismatch) | 777 | Refer (name check) |

Self-employed applicants and Category B employers without salary slips are always Refer. An email on a disposable domain (e.g. `@mailinator.com`) gives a Hunter Refer. Approve and Reject open a decision dialog that shows the credit summary. **Notes are required** when the decision goes against the recommendation (approving a Refer/Decline, or rejecting an Approve). Applications underwritten before the Credit Review existed show plain detail lines: click **Re-run underwriting** to get the full reports.

**Existing customers.** After the OTP (or straight away, if they already verified in this chat for a Top-Up), answers already on file are filled in and shown back once, with the PAN masked: earlier submitted applications first, then earlier journeys, then the Contact (email, birthdate, mailing PIN/city), and EMIs from active Kotak loans. Only the missing questions are asked, numbered over what's actually asked (e.g. *1/2*). Purpose and amount are always asked again. A reply of **Change** clears the prefilled answers and asks all 10. On submit, any blank Contact fields are completed from the application, so the next application asks even less. New customers get all 10 questions.

**Inbound photos.** WhatsApp attachments arrive as Salesforce Files linked to the MessagingSession. A `ContentDocumentLink` trigger records them on the application as soon as they arrive and sends the next document prompt, so the customer doesn't need to type anything. If a file doesn't arrive, attach it to the Loan Journey record (Files related list) and reply **Done**. Customers can also reply **Skip**, and the RM collects the documents offline.

**RM uploads.** On the Loan Application page, the scorecard's Documents section has **Upload a document**: pick the type (PAN Card, Bank Statement, Salary Slips, Other), then drop or choose files (PDF/JPG/PNG/HEIC). Each file is recorded as a Loan Document with Source RM. The menu on each document marks it **Verified** or **Rejected**. After adding a missing document, click **Re-run underwriting** so the checks include it.

**Voice notes (ElevenLabs).** A customer can answer any step with a WhatsApp voice note (name and mobile, OTP, date of birth, PAN letter by letter, email, PIN, income, amounts, menu choices; English, Hindi or Marathi). The audio file publishes `LoanSeva_Voice__e`, and the subscriber user (`LoanSevaVoiceTriggerConfig`) transcribes it with ElevenLabs speech-to-text and answers the step. The reply starts with what was heard. The PAN is shown masked and the OTP is never echoed. Manual step: Setup → Named Credentials → External Credentials → **LoanSeva_ElevenLabs** → Principal **Default** → set authentication parameter **`ApiKey`** to an ElevenLabs API key with the **Speech to Text** permission. The subscriber user needs `LoanSeva_Admin`, which grants access to that principal. To switch voice off, uncheck `Voice_Enabled__c` on `LoanSeva_Config__mdt.Default`. Then audio is ignored and is never recorded as a document.

The LoanSeva LOS app and its Loan Application record page are assigned in metadata (`applications/LoanSeva_LOS.app-meta.xml`). Users with `LoanSeva_Admin` see the app; no Lightning App Builder activation is needed.

## 10. Before any external use

All rates, fees, FOIR, disbursal timelines and FAQ copy are **illustrative demo values**. Align `LoanSeva_Config__mdt` and `LoanSeva_FAQ__mdt` with Kotak's published terms, and replace the fixed demo OTP (`Demo_OTP__c`) with a real OTP provider behind a Named Credential.
